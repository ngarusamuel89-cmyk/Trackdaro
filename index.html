Reminder engine

Scheduled on the server. Not in a browser tab.

Every reminder is a durable database row with a UTC fire time, a delivery state and an idempotency key. A server-side job wakes up, evaluates due work, and dispatches through each enabled channel — no frontend timers, no lost notifications when your phone sleeps.

Exactly-once dispatch
Idempotency keys prevent duplicate emails when jobs retry.
DST & travel safe
Occurrence times are computed from the rule, then resolved in your IANA zone at fire time.
Automatic retry & fallback
If push is unavailable, the email channel still delivers. Backoff is exponential and logged.

Delivery pipeline

live
1 · Durable schedule written
Zod-validated reminder rows stored with fire_at_utc.
2 · Server cron ticks
A background worker claims due rows atomically — independent of any open browser.
3 · Localised content rendered
Dates, times and relative phrasing rendered in the recipient's timezone and locale.
4 · Multi-channel dispatch
Email via Resend first, then Web Push (VAPID) and in-app — each optional but independent.
5 · Delivery recorded & retried
Statuses persisted for audit; failures back off exponentially before alerting.

Time & time zones

Dates are hard. We made them boring.

Timestamps are stored in UTC. Your preferred timezone is stored separately as an IANA identifier. Display, reminders and recurrence all resolve against that pair — so a class at 09:00 in Nairobi stays correct whether you fly to London or daylight saving shifts underneath you.

UTC everywhere underneath

Every timestamp column is timestamptz. Conversion happens only at the presentation layer, using IANA rules — never hardcoded offsets.

DST handled by rule

Recurring classes store a wall-clock time plus a zone. Each occurrence is re-resolved, so a 08:00 lecture stays at 08:00 across daylight saving transitions.

Auto-detect with override

New profiles detect the device zone automatically via Intl, then allow a manual IANA override that's validated against the tz database.

Security & architecture

Your data stays yours. Full stop.

PostgreSQL Row Level Security enforces isolation at the database layer — not just in the UI. Every query is scoped to the authenticated user, and every mutation is validated before it touches a row.

Row Level Security policy

Even if a query is written incorrectly, Postgres refuses to return another user's rows. 

-- Users can only read their own courses
create policy "courses_select_own"
on courses for select
using ( auth.uid() = user_id );

-- Attendance never leaks across users
create policy "attendance_isolated"
on attendance_records for all
using (
  exists (
    select 1 from class_sessions s
    join courses c on c.id = s.course_id
    where s.id = session_id
      and c.user_id = auth.uid()
  )
);
